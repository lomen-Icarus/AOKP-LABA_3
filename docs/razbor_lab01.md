# Разбор лабораторной №1: тор, цвет и ECS

> Все три лабы собраны в одну программу. Код этой лабы: `src/lab1.rs`. Запуск: `cargo run -- 1` или клавиша F1 в работающей программе.

## Что от тебя требуется

Нужно написать небольшое приложение на Rust с Bevy 0.19: открыть окно, показать освещённый трёхмерный тор и управлять его цветом. Геометрию тора самостоятельно вычислять не требуется — движок предоставляет готовый примитив. Главная учебная задача: понять, где хранятся данные и как системы их изменяют.

Обязательное поведение из раздела 6 методички:

| Действие | Результат |
|---|---|
| Пробел | Следующий цвет: чёрный → белый → синий → красный → фиолетовый → снова чёрный |
| Цифры 1–5 | Прямой выбор соответствующего цвета |
| A | Включение и выключение автоматической смены |
| Автоматический режим | Новый цвет каждую секунду |
| Каждый кадр | Плавное вращение вокруг Y с учётом прошедшего времени |

Отдельно требуются `cargo fmt`, `cargo clippy` без предупреждений и отчёт. В отчёт входят титульный лист, полный текст задания, объяснение `Cargo.toml`, полный код с русскими комментариями, скриншоты нескольких цветов и сравнительная таблица обычной графической библиотеки и Bevy ECS. Это требования к сдаче; учебный разбор перед тобой помогает разобраться в решении.

## Как представить эту сцену через ECS

В привычном ООП можно было бы написать класс `Torus` с полями цвета и положения и методами `rotate()` и `change_color()`. В ECS эти роли разделены:

| Понятие | В этой лабораторной |
|---|---|
| Entity | Идентификатор конкретного тора, камеры или источника света |
| Component | Данные, прикреплённые к сущности: положение, меш, ссылка на материал |
| System | Функция, которая находит нужные данные и обрабатывает их |
| Resource | Общие данные приложения: палитра, таймер, состояние ввода |

`LabObject` — компонент-маркер без полей. Он означает: «это объект, которым управляет лабораторная». Камера тоже имеет `Transform`, поэтому запрос всех `Transform` затронул бы и её. Фильтр `With<LabObject>` оставляет только нужные сущности.

`Query<&mut Transform, With<LabObject>>` читается так: «дай изменяемые пространственные преобразования сущностей с маркером `LabObject`». Запрос описывает выборку, а цикл по нему получает совпадения. Если добавить второй тор с таким же маркером, система сможет вращать оба без отдельной функции для второго объекта.

`Res<T>` разрешает чтение общего ресурса; `ResMut<T>` — изменение. По параметрам систем Bevy определяет доступ к данным и учитывает конфликты при выполнении. Поэтому нельзя считать, что системы в кортеже автоматически выполняются слева направо: если важен порядок, его задают явно, например через `.chain()`. Это поведение описано в [документации расписаний Bevy](https://docs.rs/bevy/latest/bevy/ecs/schedule/index.html).

## Почему материал меняется не прямо в компоненте

`MeshMaterial3d<StandardMaterial>` хранит handle — идентификатор материала в хранилище. Сам `StandardMaterial`, включая `base_color`, находится в ресурсе `Assets<StandardMaterial>`.

Получается последовательность: система находит компонент тора → берёт handle → находит материал в `Assets` → изменяет `base_color`. Компонент с handle при этом можно только читать: он продолжает ссылаться на тот же материал.

Если два объекта используют один handle, изменение материала повлияет на оба. Если нужны независимые цвета, нужно создать разные материалы, даже если первоначально их свойства одинаковы.

Здесь важен комментарий **soller 666** из документа. В API Bevy 0.19 метод `get_mut()` возвращает обёртку `AssetMut`, поэтому запись должна содержать `Some(mut mat)`. Вариант из методички с `Some(mat)` нельзя механически переносить из старого примера. Обёртка предоставляет изменяемый доступ и отслеживает изменение ассета. Проверка: [Assets::get_mut](https://docs.rs/bevy/latest/bevy/prelude/struct.Assets.html#method.get_mut).

## Тор, камера и Transform

`Transform` хранит перенос, поворот и масштаб. `Transform::from_xyz(5.0, 5.0, 7.5)` ставит камеру в эту точку пространства. Следующий вызов `.looking_at(Vec3::ZERO, Vec3::Y)` поворачивает её к началу координат и использует направление Y как ориентир «вверх». Камера остаётся на прежнем месте — меняется её ориентация. Это не команда, которая потом постоянно следит за движущимся объектом: ориентация вычисляется в момент вызова. Проверка: [Transform::looking_at](https://docs.rs/bevy/latest/bevy/prelude/struct.Transform.html#method.looking_at).

Комментарий автора **«Ну, что сказать, привет»** указывает на другую неточность. `Torus::new(0.4, 1.0)` принимает **два радиуса**, внутренний и внешний. Четырёхаргументный вызов из пояснения методички для этого API неверен. Здесь радиус отверстия равен 0,4, внешний радиус — 1,0. Радиус трубки получается `(1,0 − 0,4) / 2 = 0,3`, расстояние от центра тора до центра трубки — `(1,0 + 0,4) / 2 = 0,7`. Проверка: [Torus::new](https://docs.rs/bevy/latest/bevy/prelude/struct.Torus.html#method.new).

Есть ещё визуальная ловушка: стандартный тор симметричен вокруг Y. Если крутить одноцветный тор вокруг его оси симметрии, картинка почти не изменится. Начальный наклон вокруг X делает вращение вокруг мировой Y заметным. `rotate_y()` и `rotate_local_y()` имеют разный смысл: второй поворачивает вокруг собственной оси объекта. Проверка: [Transform::rotate_y](https://docs.rs/bevy/latest/bevy/prelude/struct.Transform.html#method.rotate_y).

## Палитра, клавиатура и время

Текущий цвет определяется индексом в палитре. Формула перехода `(index + 1) % colors.len()` возвращает индекс к нулю после последнего элемента. Длина берётся из самой коллекции, чтобы добавление шестого цвета не требовало искать число `5` по всему коду. Внутренние индексы начинаются с нуля: клавиша `1` выбирает индекс `0`.

Начальный индекс и начальный материал должны совпадать. В отдельных фрагментах методички материал красный, а индекс равен нулю, то есть указывает на чёрный. Если собрать фрагменты без согласования, первый переход окажется неожиданным.

Для переключений используется `just_pressed`: один переход при новом нажатии. `pressed` подходит для непрерывного действия при удержании, например движения персонажа, но заставил бы цвета переключаться каждый кадр. Проверка: [ButtonInput](https://docs.rs/bevy/latest/bevy/input/struct.ButtonInput.html).

Вращение рассчитывается по формуле `угол = скорость × время_кадра`. В приложенном коде скорость равна **0,7 рад/с**:

| Частота | Время кадра | Поворот за кадр | Поворот за секунду |
|---|---:|---:|---:|
| 30 FPS | 1/30 с | ≈0,02333 рад | 0,7 рад |
| 60 FPS | 1/60 с | ≈0,01167 рад | 0,7 рад |
| 120 FPS | 1/120 с | ≈0,00583 рад | 0,7 рад |

Если вместо этого прибавлять фиксированные 0,01 рад каждый кадр, получатся скорости 0,3, 0,6 и 1,2 рад/с. На быстром компьютере объект будет двигаться быстрее. Ресурс `Time` даёт длительность кадра: `delta_secs()` — число секунд для вращения, `delta()` — `Duration` для таймера. Обычный `Res<Time>` в `Update` представляет игровое время, которое движок может масштабировать и приостанавливать. Проверка: [Time](https://docs.rs/bevy/latest/bevy/prelude/struct.Time.html).

`Timer::from_seconds(1.0, TimerMode::Repeating)` хранит повторяющийся интервал. Сам по себе он не создаёт поток и не запускает функцию раз в секунду. Система каждый кадр вызывает `tick(time.delta())`, а `just_finished()` сообщает, завершился ли интервал при этом обновлении. `State<AutoColorState>` хранит текущий режим; `NextState` запрашивает переход, который применяется расписанием состояний. Проверка: [Timer](https://docs.rs/bevy/latest/bevy/prelude/struct.Timer.html), [NextState](https://docs.rs/bevy/latest/bevy/prelude/enum.NextState.html).

## Как устроен код лабы 1 (src/lab1.rs)

Начальный цвет — чёрный, автоматический режим выключен. `Lab01Plugin` регистрирует ресурсы и системы. `setup_torus` создаёт сцену при входе в лабу 1: тор наклонён на 0,65 рад вокруг X, камера стоит в `(2.8, 2.0, 3.5)`.

Обновление цвета разделено на три последовательных шага:

1. `keyboard_input_system` обрабатывает клавиши и меняет индекс палитры. При одновременном нажатии цифры и Пробела выигрывает цифра; среди нескольких цифр — меньшая.
2. `auto_color_system` меняет индекс по таймеру, когда состояние `On`.
3. `apply_color_system` переносит цвет из изменившейся палитры в материал. Если палитра не менялась, работа пропускается.

Ручной выбор и клавиша A сбрасывают таймер. Флаг `skip_tick` не позволяет автоматике сразу перескочить ещё на один цвет в том же кадре. После ручного выбора новый цвет получает полный секундный интервал. `rotation_system` работает отдельно и продолжает вращение при выключенной автоматической смене.

## Что означает Cargo.toml

В `[package]` заданы имя и версия твоей программы, а `edition` выбирает редакцию Rust. В `[dependencies]` перечислены библиотеки. Версия собственной лабы `0.1.0` и версия движка `0.19` — разные вещи.

`Cargo.toml` описывает допустимые зависимости и настройки, `Cargo.lock` фиксирует реально выбранные версии, включая вложенные зависимости. Для приложения lock-файл стоит сохранять вместе с исходниками: другому человеку будет проще повторить сборку. Ручное редактирование списка зависимостей внутри lock-файла не требуется. Проверка: [Cargo.toml и Cargo.lock](https://doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html).

Профили с `opt-level = 1` для проекта и `3` для зависимостей направлены на скорость **выполнения**. Утверждение методички, что оптимизация не замедляет компиляцию зависимостей, неверно: первая сборка обычно дольше. Повторная разработка выигрывает от сохранённых результатов сборки. Проверка: [профили Cargo](https://doc.rust-lang.org/cargo/reference/profiles.html).

## Как написать свою версию и сравнить

1. Создай проект и открой пустое окно. Разберись с `App`, `DefaultPlugins`, `run()`.
2. Добавь тор, материал, камеру и свет. Проверь сцену до обработки клавиш. `Startup` запускается при старте, а не заново каждый кадр.
3. Добавь маркер, палитру и только Пробел. Пройди полный круг цветов.
4. Реализуй цифры. Выбери фиолетовый и нажми Пробел: должен получиться чёрный.
5. Добавь вращение с `delta_secs()`. Объясни единицы измерения каждого множителя.
6. Добавь состояние и таймер. Реши явно, начинается ли секунда заново при включении режима и ручном выборе цвета.
7. Проверь удержание клавиш и совпадение ручного нажатия с таймером. Затем запусти форматирование и линтер.

Для сравнения решений смотри сначала на поведение и распределение ответственности. Одинаковые имена функций и число строк ничего не доказывают.

Попробуй три изменения самостоятельно: добавь зелёный цвет; сделай второй тор с независимым материалом; временно замени вращение с `delta_secs()` фиксированным шагом и рассчитай различие при 30 и 120 FPS.

## Вопросы для защиты

| Вопрос | Короткий ответ |
|---|---|
| Зачем маркер без полей? | Чтобы выбирать нужные сущности по наличию компонента. |
| Почему палитра — ресурс? | В этой программе она общая для управления объектами. |
| Где хранится цвет? | В `StandardMaterial`, на который указывает компонент с handle. |
| Зачем `mut mat`? | Изменение проходит через изменяемую обёртку `AssetMut`. |
| Что обеспечивает независимость вращения от FPS? | Умножение скорости на длительность кадра. |
| Таймер — это отдельный поток? | Нет, система обновляет его накопленное время. |
| Зачем `% colors.len()`? | Для циклического перехода к первому цвету. |
| Почему красивый скриншот не доказывает всю работу? | Он не проверяет клавиши, таймер и зависимость скорости от FPS. |
